**Status:** DONE (2026-06-25)  
**Milestone:** M46  
**Verdict:** Scenario A1 — Separate-ledger confirmed (host boundary: `/fapi` vs `/sapi`)  
**Branch:** `feat/m46-rate-limit-ledger-audit`

## Context

The engine's local token bucket for `REQUEST_WEIGHT_1M` reported `localUsed ≈ 240–280 / 1920` while Binance's `X-MBX-USED-WEIGHT-1M` response header consistently returned `≈ 1–6 / 1920` — a two-order-of-magnitude disagreement that masked a correctness gap: a possible second IP-level weight ledger the engine was unaware of, leaving either under-counting (invisible 429 approaching) or over-counting (unnecessary throttle) undetected.

H4 was deferred from M17/M18 after the directional drift alert (M18) silenced the operational pain without understanding the root ledger structure. This milestone re-opens the investigation with evidence-led classification.

---

## Investigation findings (I1–I4)

### I1 — Binance ledger structure (Binance API docs + ccxt surface)

**Finding:** Binance Futures REST traffic crosses **two distinct host processes**, each maintaining its own independent per-IP `REQUEST_WEIGHT` ledger:

| Endpoint host | Endpoints served | REQUEST_WEIGHT ledger | Header exposed | Engine isolation |
|---|---|---|---|---|
| `/fapi/*` | Public market-data (`fetchOpenInterest`, `fetchFundingRate`, `fetchTickers`, `loadMarkets`) + authenticated account (`fetchPositions`, `fetchBalance`, `fetchOpenOrders`, order ops) | **Shared single ledger (per-IP, 1-min rolling, 2400 units)** | One `X-MBX-USED-WEIGHT-1M` | None (conflated pre-M46) |
| `/sapi/*` | Boot-time spot API calls (`sapiGetAccountApiRestrictions*` per ADR 0028) | **Separate ledger (per-IP, 1-min rolling, 2400 units)** | One `X-MBX-USED-WEIGHT-1M` (same name, different host) | Must be isolated |

**Key finding:** The two hosts' `X-MBX-USED-WEIGHT-1M` headers **share the name but report unrelated per-IP ledgers on different host processes.** Pre-M46, `CcxtBinanceExchangeClient` held a single `last_response_headers` slot; after a `/sapi` call (boot-time key-permission check), `reconcileFromHeaders()` mistakenly wrote the `/sapi` header's value into the `/fapi` `REQUEST_WEIGHT_1M` bucket. The observed near-zero `/fapi` header (`≈1–6` even during a 240-weight burst) was the idle `/sapi` ledger's count, not the `/fapi` ledger's actual state.

**Explicit answers to I1 questions:**

1. **Do `/fapi` market-data and account endpoints share one REQUEST_WEIGHT ledger?** Yes. Both share the single `/fapi` per-IP 1-min ledger.
2. **Does the market-data ledger expose a distinct readable header?** No. The `/fapi` market-data and `/fapi` account endpoints both report via the same single `X-MBX-USED-WEIGHT-1M` header on the `/fapi` host. There is no second readable header for a market-data sub-ledger within `/fapi`.

### I2 — Live header evidence (read-only capture)

**Captured state:** Engine's local `localUsed ≈ 240–280 / 1920` (from steady-state poll cycle) vs Binance `X-MBX-USED-WEIGHT-1M ≈ 1–6 / 1920` (from live response header).

**Classification:**  
- Pre-M46 engine routed **all** REST calls (market-data + account) through one bucket, reconciling against **one slot** that carried the most recent response.
- Boot-time `/sapi` key-permission checks wrote `/sapi` header (idle, ledger at ~1–6 units) to the `/fapi` bucket slot.
- Steady-state poll cycles (100 OI + 100 funding + 1 ticker = 240-unit burst on `/fapi` ledger) ran while the slot held stale `/sapi` data.
- Result: the engine charged correctly locally (~240–280 per cycle) but read a persistently near-zero header because the slot was showing the wrong host's ledger.

### I3 — Local charge arithmetic audit

**Steady-state per-minute charge in the poll loop:**

```
100 symbols × fetchOpenInterest (weight 1) = 100
100 symbols × fetchFundingRate (weight 1) = 100
1 × fetchTickers (weight 40) = 40
Reconciliation ops (fetch{Positions,OpenOrders,Balance}, weight ≤5 each) ≈ 5–15 per minute (cadence-dependent)
Total gross per cycle ≈ 245–255
```

**Measured `localUsed ≈ 240–280 / 1920` on a 1920-capacity bucket with continuous refill:**  
The steady-state `localUsed` reflects the instantaneous balance after the cycle debit minus the inter-cycle continuous refill. A 240 gross charge minus ~10 refilled = ~230 used, which matches observations. This **confirms local arithmetic is correct**; the disagreement is **isolated to the header reconciliation**, not a local-accounting bug.

**Weight-table verification:** Every `/fapi` operation in `OPERATION_REQUEST_WEIGHTS` matches its Binance-documented per-endpoint weight. No stale entries.

### I4 — Classification (Verdict A1)

**Conclusion: Scenario A1 — Separate-ledger confirmed.**

Evidence:
- I1 confirms `/fapi` and `/sapi` are **two distinct per-IP ledgers on different hosts**.
- I1 also confirms there is **no second readable `/fapi` market-data header** — the single `/fapi` `X-MBX-USED-WEIGHT-1M` header includes both market-data and account weight.
- I2 shows the engine was conflating the two host ledgers via a single `last_response_headers` slot.
- I3 shows local arithmetic is correct; the discrepancy is not a weight-table error.
- The persistent near-zero (`≈1–6`) header during a 240-unit burst rules out Scenario C (Scenario C requires the header to climb measurably during a burst to be credible as a conservative-model artifact).

**Rationale for rejecting Scenario A2 (split within `/fapi`):**  
A2 would split `/fapi` into market-data vs account buckets. But the `/fapi` `X-MBX-USED-WEIGHT-1M` header reports **combined** market-data + account weight for the single ledger — there is no per-type sub-header. If the account bucket were reconciled against this combined header, it would see inflated `headerUsed > localUsed` signals every time a market-data burst ran, triggering spurious `RATE_LIMIT_DRIFT` false alarms. The ledger boundary Binance enforces is the **host** (`/fapi` vs `/sapi`), so the split must follow the host boundary (A1), not the endpoint-type boundary (A2).

## Implementation (Scenario A1)

### Changes shipped

1. **New `SAPI_REQUEST_WEIGHT_1M` bucket** in `RateLimitPolicyService`:
   - Scope: per IP, `/sapi` host, 1-minute rolling
   - Capacity: `floor(2400 × 0.80) = 1920` (same 80% safety margin)
   - **Local-only** — no header reconciliation (the `/sapi` header cannot be reliably distinguished from the `/fapi` header in the single `last_response_headers` slot)
   - Boot-only traffic (`sapiGetAccountApiRestrictions*` calls at startup) carries negligible weight (handful of weight-1 calls), so pure conservative local accounting poses no realistic ban risk

2. **Operation-to-bucket routing** via updated `OPERATION_REQUEST_WEIGHTS`:
   - `sapiGetAccountApiRestrictions*` → `SAPI_REQUEST_WEIGHT_1M`
   - All other weighted operations → `/fapi` `REQUEST_WEIGHT_1M`
   - Routing is explicit in the weight-table, not inferred at call site (preserves ADR 0030 §2.2 contract)

3. **`allBuckets` inclusion** (hard constraint):
   - `SAPI_REQUEST_WEIGHT_1M` added to the `allBuckets` getter
   - `engageFreeze()` (on 418 IP ban) now drains and suspends **both** `/fapi` `REQUEST_WEIGHT_1M` and `SAPI_REQUEST_WEIGHT_1M` together
   - Rationale: a 418 IP ban applies to the **IP** (covers both `/fapi` and `/sapi` hosts); keeping `sapi` outside the freeze would allow it to keep issuing calls into a banned IP, defeating the freeze protection

4. **ADR 0030 amendment** (§2.7 — dual-host ledger separation):
   - Documents the finding (I1–I4 evidence)
   - Documents the A1 decision and why A2 is rejected
   - Documents the `/sapi`-bucket-is-local-only design and the `allBuckets` hard constraint
   - Amended 2026-06-24 by architect; scribe has reviewed for accuracy

5. **`reconcileFromHeaders()` contract** — **unchanged**:
   - `REQUEST_WEIGHT_1M` reconciliation now receives **only `/fapi` responses** (because `/sapi` operations are routed to the new bucket)
   - No explicit host-aware header logic needed; bucket targeting (via `weightBucketFor()`) ensures market-data/account calls charge `/fapi` bucket, boot `/sapi` calls charge `/sapi` bucket
